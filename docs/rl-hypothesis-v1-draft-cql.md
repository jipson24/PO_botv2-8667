# Гипотеза развития: offline RL (CQL) как следующий слой над Rule-based симулятором

**Статус: черновик, гипотеза. Не согласовано с пользователем. Не внедряется в
боевой движок ни в каком виде до отдельного одобрения по протоколу изменений
(см. `AGENTS_PO_bot.md`, раздел "Протокол изменений движка").**

Дата черновика: 2026-09-25.

---

## 1. Зачем этот документ

Регламент проекта уже описывает "Имитационную площадку" — Rule Set / Replay
Engine / Scorer на декларативных JSON-правилах (`snapshot → decision`). Это
первый и обязательный слой: он даёт статистически честную проверку конкретных,
интерпретируемых гипотез ("добавить фильтр ADX > 25" и т.п.).

Этот документ — гипотеза **следующего** слоя, который встаёт поверх
накопленной базы слепков, когда её станет достаточно: заменить перебор
вручную заданных правил на модель, которая учится напрямую по историческим
слепкам, какие входы статистически оправданы. Явно фиксируется **как именно**
это должно быть сделано, чтобы не повторить ошибку "чёрного ящика для
автоторговли" — это запрещено регламентом отдельно.

## 2. Почему не обычный RL, а offline RL, и почему конкретно CQL

Задача **не** классический RL с онлайн-взаимодействием со средой:

- Сделки по бинарным опционам не образуют последовательный процесс с переносом
  состояния — исход одной сделки не меняет "мир" для следующей (в отличие от,
  например, управления позицией/капиталом). Формально это ближе к
  **contextual bandit**: контекст = слепок, действие = {call, put, skip},
  награда = бинарный исход с учётом payout.
- У нас нет возможности пробовать новые действия в реальности без риска — вся
  обучающая база это логи **уже принятых решений одной фиксированной
  политики** (текущий движок сигналов). Это классический сценарий **offline
  (batch) RL**: учиться по логам без дополнительного взаимодействия со средой.
- Главная опасность offline RL — **extrapolation/overestimation error**:
  модель переоценивает действия, которые редко или никогда не встречались в
  логах, потому что для них нет данных, опровергающих оптимизм. При нашем
  объёме данных (см. §4) это не теоретический риск, а гарантированный исход
  без защиты.
- **CQL (Conservative Q-Learning)** — метод, который прямо штрафует
  Q-значения для action-state пар, слабо покрытых логами, вместо того чтобы
  доверять им. Это подходящий выбор именно потому, что он консервативен по
  построению — предпочитаем "недооценить непроверенное", а не "переоценить
  и потом слить депозит на реальном счёте". Альтернативы (обычный DQN/offline
  Q-learning без консервативной регуляризации) для такого маленького и
  нестационарного датасета не рассматриваются как первый шаг.

## 3. Формальная постановка (черновик)

- **State (контекст)**: содержимое `EntrySnapshot` v3 — индикаторы на момент
  входа (RSI, MACD, ATR, структура рынка), OHLC-окно до входа, час киевских
  суток, payout, флаг OTC. Явно **не** включает будущие бары — только то, что
  было известно на момент решения.
- **Action**: `call` / `put` / `skip` (или дискретизированный уровень
  confidence, если потребуется более тонкое управление, — отдельным
  расширением, не в первой версии).
- **Reward**: `+1 * payout_fraction` при win, `-1` при loss, `0` при draw/skip.
  Без сглаживания и без "мягких" промежуточных наград — сделка либо
  выигрывает, либо нет, это и есть честный сигнал.
- **Policy, обучаемая offline**: CQL поверх логированных `(state, action,
  reward)` троек из базы сигналов, где `action` = решение движка (call/put),
  а для действия `skip` — troек **не существует по определению** (движок не
  логирует то, что не отправил как сигнал). Это структурная дыра, разобрана в
  §5.

## 4. Готовность данных — жёсткий гейт перед стартом

Проверено в текущей сессии (2026-09-25, база сигналов):

| Показатель | Значение |
|---|---|
| Всего сигналов в базе | 792 |
| Со слепком любой версии | 744 |
| Со слепком **v3** (актуальная версия, поддерживает пост-входные бары) | 281 |
| С фактически заполненными `postentryCandles` | 38 |

**Вывод: данных категорически недостаточно для offline RL уже сейчас.**
281 слепок v3 — это меньше одного дня плотной торговли по большинству
таймфреймов проекта, а полезны для доверенной оценки только те 38, где
пост-входное окно реально дозаписано (без него часть "что было после входа"
недосчитываема, и не все признаки восстановимы). Здравый ориентир для
**первой** содержательной попытки CQL — не менее нескольких тысяч слепков v3
с заполненным `postentryCandles`, и это не гарантия успеха, а минимальная
планка, чтобы попытка не была заведомо шумом.

**До достижения этой планки этот документ — только гипотеза для обсуждения,
работа над ней не начинается.** Приоритет остаётся за Rule-based симулятором
(п.1 регламента — он уже применим к 281 слепку v3, RL к ним не применим
содержательно).

## 5. Известные структурные проблемы, которые нужно решить до, а не во время обучения

1. **Нет логов действия `skip`.** Движок логирует только то, что решил
   отправить как сигнал. Contextual bandit / offline RL без примеров действия
   "не входить" систематически недооценивает ценность пропуска сделки —
   ровно то, что должно быть одним из главных источников edge (см. цель №1
   регламента: "отсекание условий входа с низким edge"). **Требуется**
   отдельное решение: либо логировать состояния, где движок рассматривал вход
   и отказался (с причиной отказа — `blockers`), либо не относиться к `skip`
   как к обучаемому действию в первой версии, а тренировать модель только на
   `call`/`put` и обрабатывать порог "не входить" отдельным калиброванным
   thresholding по итоговому score модели (проще, но менее честно как RL).
2. **Нестационарность рынка/брокера.** Условия, при которых обучались старые
   слепки (v2, 463 шт., без пост-входного окна — не годятся для этой задачи
   вообще), и текущие могут отличаться (другой набор активов, другой payout,
   сезонность). Offline RL особенно чувствителен к сдвигу распределения между
   train и деплоем. Обязателен walk-forward, а не просто train/holdout split
   по регламенту — тестовый период должен идти строго после train по времени.
3. **Экзотические OTC-пары с недостижимой историей** (`KESUSD_otc` и
   аналогичные — см. диагностику блокировки очереди пост-входного захвата в
   этом чате) искажают датасет: у них систематически нет `postentryCandles`.
   Если их не исключить или не пометить отдельно, модель обучится на
   нерепрезентативной выборке по этим символам. Решение по исключению таких
   пар из отслеживаемых активов — открытый вопрос, не согласован с
   пользователем, вынести на отдельное обсуждение до старта RL-этапа.
4. **Малость выборки относительно размерности state.** Даже при нескольких
   тысячах слепков, если состояние содержит десятки признаков, риск
   переобучения CQL высокий. Первая версия должна использовать урезанный,
   заранее отобранный набор признаков (не весь `EntrySnapshot` целиком), с
   явным списком фичей, зафиксированным в конфиге версии — не "дать модели
   всё и посмотреть".

## 6. Этапы внедрения (черновик порядка, часть общего протокола изменений)

Ни один этап не начинается автоматически — переход к следующему требует
отдельного явного одобрения пользователя, отдельно от этого документа.

1. **Гейт данных.** Дождаться накопления слепков v3 с заполненным
   `postentryCandles` до ориентировочной планки (см. §4) и закрыть дырку
   логирования `skip` (§5.1) — иначе этап 2 не имеет смысла начинать.
2. **Baseline на Rule-based симуляторе.** Прежде чем сравнивать с CQL, должен
   существовать зафиксированный, воспроизводимый результат текущего
   Rule-based Replay Engine на train/holdout — это baseline, с которым CQL
   сравнивается на **одном и том же** holdout, а не на разных нарезках.
3. **Отбор признаков и action-space, зафиксированные в конфиге версии**
   (например, `rl-v1-draft-cql.json`) — до кода, по аналогии с Rule Set из
   регламента.
4. **Обучение CQL на train-подмножестве**, walk-forward по времени.
5. **Оценка на holdout** — winrate, доверительный интервал, сравнение с
   Rule-based baseline **и** со стратегией "ничего не менять" (чистый
   текущий боевой движок). Модель, которая не бьёт оба baseline с
   статистически значимым отрывом на holdout, отклоняется — независимо от
   того, как эффектно она выглядела на train.
6. **Согласование с пользователем** с полным отчётом (формат — HTML+SVG по
   регламенту), включая раздел "почему могло не сработать", если не
   сработало.
7. Только после одобрения — рассмотрение переноса в боевой контур, и только
   как **диагностический инструмент поддержки решения**, не как автономный
   автоторговый агент — автоторговля вне рамок этого документа и остаётся
   решением, которое пользователь принимает отдельно и позже (см. регламент).

## 7. Критерии, при которых гипотеза считается непригодной

- Данных не набирается до нужного объёма за разумный срок (например, темп
  роста `postentryCandles` слишком низкий из-за физических ограничений фида
  по многим парам) — тогда офлайн RL откладывается на неопределённый срок в
  пользу Rule-based подхода, это не провал, а честный вывод по §8 регламента.
- CQL показывает эффект на train, но не подтверждает его на holdout —
  отклоняется без попыток "подкрутить" постфактум (регламент, п. "Ключевая
  ловушка — переобучение").
- Эффект есть, но статистически неотличим от Rule-based baseline при текущем
  размере выборки — версия помечается "требует больше данных", не "успех".

## 8. Что нужно от пользователя, когда придёт время

- Подтверждение, что дырка с логированием `skip` (§5.1) закрывается именно
  предложенным способом (или альтернатива).
- Решение по исключению/сохранению нежизнеспособных OTC-пар (§5.3).
- Согласование конкретного набора признаков и action-space перед началом
  обучения (§6, этап 3).
- Финальное согласование результата перед любым переносом за пределы
  симулятора (§6, этап 7) — как и любое изменение боевого движка.
